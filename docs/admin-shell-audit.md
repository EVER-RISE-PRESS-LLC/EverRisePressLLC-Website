# Publisher workspace: shell, overview, and sign-in audit

Audit and implementation: 27 October 2026. Scope is the shared admin shell, navigation, appearance controls, user menu, page heading, empty and KPI states, overview, and sign-in. Reviewed against the existing PRODUCT.md, docs/DESIGN.md, source routes, D1 schema, dashboard queries, authentication guard, and shadcn primitives. The established charcoal, cream, gold, and Karla identity is preserved. The admin surface follows Operate mode: task clarity and legibility take priority over display typography.

## Concrete findings and fixes

| The same six links had no task grouping. A generic “Publisher Control Room” header did not identify the open page. | Staff had to remember where work lived and lost context inside editors. | Grouped navigation into workspace, publishing, and audience; added section and editor breadcrumbs with useful names instead of database IDs. ## Resource and scope constraints

No service, dependency, billing setting, account, password, reader record, referral partner, or catalog record was changed by this work. The overview reads the existing Worker/D1 deployment and article store. No paid analytics or external dashboard is required. UI copy does not promise email delivery or treat retailer click events as verified sales.

The historical admin specification requested dark by default and document rem scaling; this redesign intentionally uses this redesign's readable light default and a temporary route-only body scale so Radix portals and the page stay consistent without changing public document settings.

## Verification and remaining limits

The main integration pass is responsible for the production build, Cloudflare deployment, and combined desktop/mobile browser QA across all editors. This audit does not claim a live production sign-in or mutate real data. The article helpers added by the main implementation are asynchronous and supply `id`, `savedAt`, and `isLive`; the overview uses those fields rather than stale repository draft counts.

Charts reflect first-party recorded events. Their referral ratio is not a cohort conversion metric, clicks may repeat, and retailer links cannot establish completed purchases. The interface states those limits directly.

## Sign-in endpoint follow-up

The existing login endpoint accepted untyped JSON via optional property access, so object or array inputs could throw; bodies were not bounded, no failed-attempt limit existed, and restricted roles received an account-specific access response. The endpoint now checks same origin and JSON media type, limits the body to 4096 bytes, validates string fields before use, normalizes email without changing the password, and returns clear 400/413/415 responses for invalid input. Credential failures use the same response for missing users, wrong passwords, and nonstaff accounts. Missing-user attempts still perform PBKDF verification work.

The existing D1 database stores only a hash of the Cloudflare client address, failure count, and reset timestamp for the limit. Atomic upsert allows at most ten failed attempts per 15-minute window, does not extend an active window on every failure, returns a `Retry-After` header with 429, expires old buckets, and clears a successful user's address bucket. It introduces no external rate-limit service or billing requirement. Operational errors fail closed with a 503 and never log credentials, request bodies, or detailed database errors. The existing session cookie name, lifetime, security attributes, and password hashing remain unchanged.

Validation performed for this scope:

- Targeted ESLint passed for all changed shell, overview, sign-in, and boundary files and for the login API.
- Impeccable's mechanical detector returned no findings for the changed UI targets.
- A local in-memory SQLite/API harness exercised the actual endpoint, shared JSON/origin helpers, PBKDF verification, and JWT generation. It passed malformed field types, malformed JSON, oversized request, cross-origin request, wrong media type, successful existing-password authentication, session-cookie verification, generic nonstaff rejection, expiration, successful bucket clearing, 429 retry headers, hashed client-address storage, and twelve concurrent failures without lost counter updates. The harness made no production request and used only disposable fixtures.
- The first TypeScript pass found only pending cross-agent integration fields (`savedAt`, `isLive`, article `id`) and the not-yet-created shared MediaPicker. The main integration pass will rerun type checking after those files land.

## Article backend integration follow-up

Article editing now uses the existing D1 database rather than repository JSON. The saved draft and the approved public snapshot are separate. Draft saves preserve incomplete metadata, never overwrite the live snapshot, sanitize rich text, and return optimistic revisions. Explicit publication requires a confirmed byline, finished body text, useful title and description, category, cover alternative text, complete HTTPS supporting sources, valid structured blocks, and an affirmative review confirmation. The server records the real staff reviewer and publication/update timestamps. The first publication date and article address remain fixed after unpublishing and republication.

Archive preserves both snapshots and removes the article from public queries; restore reverses the archive and restores its prior visibility. A saved draft that differs from a live snapshot receives an unpublished-changes state. Private editorial notes stay in the draft and are cleared from public snapshots and public getter results. Visibility actions preserve any supplied unsaved draft work, preventing a fast archive or unpublish from discarding words typed during the autosave debounce.

The async catalog is backed only by D1, uses React request caching, and has no repository fallback. `src/lib/db/seed-article-briefs.sql` explicitly imports the two existing briefs without overwriting later staff work. Migration 0004 adds persistent publication history and the login-expiry index to databases that already applied 0003. Only local D1 received migration 0004 and the idempotent brief import during this work; no production database write occurred.

Added portable tests: `scripts/admin-articles.test.mjs`, `scripts/admin-article-api.test.mjs`, and `scripts/admin-login-api.test.mjs`. Together with the existing blog tests, 20 tests pass. They exercise actual article handlers and store SQL, actual session JWT and staff-role checks, CSRF and body limits, draft flexibility, publication gating, server-owned dates/reviewer, revision/address conflict distinction, concurrent updates, public snapshot preservation, archive/restore, private-note boundaries, safe content, idempotent import, and the actual login PBKDF/rate-limit endpoint. Only Cloudflare context and disposable user lookup are substituted; no production requests are made. Targeted ESLint passes for the backend and all three test files.


Publication dates reflect public changes, rather than button presses. Repeating Publish with unchanged public fields, including a publish request that only saves a private editorial note, preserves the existing public modification timestamp and original review record. The staff save timestamp and optimistic revision can still advance to record the actual operation. A material change to public article fields receives a new server timestamp and reviewer record; the original publication date stays fixed. Review confirmation remains mandatory for every publish request. A regression test verifies unchanged, note-only, and material-change behavior.


The 130–150% browser QA pass exposed a portal-coordinate bug in body zoom: Floating UI's physical anchor coordinates were scaled again, pushing menus off screen. Workspace scaling now applies only to `.admin-root`; the body and Radix portals remain unzoomed, while the temporary admin body marker still supplies matching theme tokens. Menus, dialogs, and notifications remain at standard size with readable controls. The appearance menu names the setting Workspace size and explains the boundary. Scaled viewport heights are divided by the workspace factor so the sidebar and sign-in surface fit the real viewport. Public page styling remains unchanged. Runtime confirmation of this correction is part of the parent integration QA pass.
